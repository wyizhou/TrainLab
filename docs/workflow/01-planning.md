# 阶段一：规划

## 目标

在动代码前把任务边界和完成条件说清楚。规划是当前开发任务的一部分，不需要启动独立 Planner，也不需要写 pending 提案或 `.blocked` 文件。

## 必做检查

1. 阅读用户当前要求与 `docs/project-state.json`。
2. 查看工作区状态，识别已有未提交改动。
3. 找到相关代码、测试和设计基线。
4. 涉及 UI 时核对 v3.2 对应页面、断点和交互状态。
5. 明确依赖、风险与尚未解决的冲突。

## 规划结果

至少明确以下内容：

- 范围：本次修改哪些页面、组件或行为。
- 非范围：明确哪些相关内容本次不动。
- 验收标准：每一条都能通过测试、浏览器检查或人工对照判断。
- 验证方式：单测、e2e、视觉基线、类型检查、lint、build 中需要哪些。

普通任务把这些内容放在 Codex 的任务计划和进度说明中即可。只有跨多轮的大型里程碑才需要更新 `docs/backlog.md` 或增加专项设计文档。

## 停止条件

以下情况不应自行猜测后继续：

- 用户要求与原型直接冲突，并且会改变功能或视觉结果。
- 必需 fixture、账号状态或数据不存在。
- 修改会引入真实外部调用、数据删除或其他超出授权的副作用。
