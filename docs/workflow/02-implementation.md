# 阶段二：实现

## 目标

在规划阶段确定的范围内直接完成代码和测试。主 Agent 承担 Executor 与集成职责；默认保持单一工作区和单一写入者，不通过旧 harness 状态文件取件。大型任务采用已批准的 worktree 并行方案时，每个 worktree 仍必须保持唯一写入者。

## 工作原则

- 先理解现有组件和数据流，再修改；优先扩展现有实现。
- 保持改动聚焦，不顺带重构无关区域。
- 保留用户已有修改，不使用破坏性命令清空工作区。
- 行为修改同步补单测；用户旅程、响应式和视觉契约修改同步补 e2e。
- UI 实现同时检查整页结构和局部 computed 样式，不能只让单个锚点通过。
- 继续集中使用 `frontend/src/styles/` 中的设计 token，并保持 `data-vc` 锚点稳定。
- 外部设计导出只读；所有实现写入限定在仓库内，不修改外部源，也不把其本机绝对路径持久化到仓库。
- 实现侧视觉回归资产只能在对应设计修订已被明确实现后更新，不能通过改基线来迁就错误实现。
- 前端修改限定在 `frontend/`，后端修改限定在 `backend/`；跨端契约和共享项目状态放在根 `docs/`，不在两端各维护一份相互漂移的版本。

## Worktree 并行实现

经规划确认可并行时，按以下顺序执行：

1. 集成负责人从最新目标分支建立集成分支和集成 worktree，先完成并验收公共基础。
2. 记录公共基础提交；所有独立单元都从这个明确提交创建各自分支和 worktree，不从漂移中的工作区随意分叉。
3. 每个子 Agent 只领取一个交付单元，先复述范围、文件边界和验收命令，再在自己的 worktree 修改、测试和提交。
4. 子 Agent 不改集成分支、不直接合并、不推送 `main`；发现必须越过文件边界或改变公共契约时停止并报告，由集成负责人重新规划。
5. 集成负责人检查提交范围和证据，按依赖顺序逐个合入；共享注册、锁文件、迁移链头、聚合文档和冲突统一在集成 worktree 处理。
6. 每合入一个单元即运行该单元相关回归；失败先修复再继续，不能把多个未知失败堆到最后。
7. 全部单元合入后由集成负责人完成跨单元测试、文档和项目状态收口，再进入最终验收。

并行期间不允许多个 Agent 共享一个 worktree，也不允许通过复制未提交文件跨 worktree 传递工作。单元间只通过已提交、可审计的 Git 变更和冻结契约协作。

## 完成条件

进入验收阶段前应满足：

- 规划范围内的功能已实现。
- 相关测试已新增或更新。
- 没有临时文件、调试输出或无关格式化改动。
- 已知限制和未完成项能够明确说明。
- 使用并行方案时，每个单元均有独立提交与验收证据，集成分支没有遗漏提交、未解决冲突或来源不明的改动。
