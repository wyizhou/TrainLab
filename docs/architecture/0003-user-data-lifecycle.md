# ADR 0003：用户数据生命周期与私有存储配额

状态：已采纳

## 决策

- 活动解析标题和用户显示名覆盖分别保存；覆盖字段属于导入记录，解析重放或派生活动重建不能清除用户命名。
- 导入状态扩展为 `pending/processing/complete/partial/failed/deleting/delete_failed`。所有列表、重试、删除和活动可见性复用同一组状态常量，不建立平行状态机。
- 删除先锁用户行，再锁导入行并提交 `deleting`，随后幂等删除私有原文件，最后硬删导入行并级联派生数据。文件或最终数据库提交失败保留可恢复状态，重复 DELETE 继续完成；不存在和跨用户对象统一返回 `204`。
- 每次解析生成不可猜测的 `processing_token`。解析终态写入必须重新取得导入行锁，同时验证 `status=processing` 与 token；删除或新解析接管会清除/替换 token，旧解析不能覆盖删除状态或复活活动。
- 每用户默认限制 5 GiB、10,000 个已登记原文件。上传按“用户行锁→清理该用户无引用残留→隔离暂存→重复 SHA→用量判断→原子提升→登记提交”的顺序执行，避免并发请求各自检查通过后合计超限。
- 暂存路径固定在用户目录下的 `.staging`，最终文件继续使用服务端生成的用户 UUID/导入 UUID。提升用不覆盖现有目标的 hard link；提升中途失败补偿删除最终链接。数据库或文件系统正常失败时回滚并清理可定位的两侧残留。
- `trainlab reconcile-storage` 只扫描服务端生成的 UUID 文件名，默认 dry-run。只有显式 `--apply` 才删除超过正整数宽限期、且没有数据库引用的文件；每个用户扫描期间取得用户行锁，避免误删合法在途文件。报告只含数量和字节数，不输出私有路径。
- 当前仍使用同步请求内解析、单体 FastAPI 和 PostgreSQL，不为数据生命周期提前引入 Redis、队列、微服务、回收站或云备份。

## 原因

真实删除、解析重放和并发上传会同时触及数据库与文件系统，单纯依靠请求顺序或进程内锁无法覆盖多 worker、崩溃和重试。数据库行锁、状态/token fencing、隔离暂存与幂等补偿共同提供可恢复边界，同时保持当前部署足够简单。

## 后果

- 数据库迁移头为 `0003_activity_data_lifecycle`；降级只移除本里程碑字段和索引，不删除既有导入、活动或原文件。
- 已登记用量以 `activity_imports` 为事实来源，包含失败和删除未完成记录；只有硬删除完成才释放配额。
- 在线删除不会修改已经生成的离线备份。恢复旧备份可能恢复已在线删除的数据，备份保留、访问和销毁策略必须独立执行。
- 数据库和私有卷仍必须作为同一时间点的恢复单元；孤儿审计不能替代备份，也不能根据文件名猜测归属。
- 当前前端没有新增重命名、删除、导入管理或配额界面；后续 UI 必须基于当次外部设计输入单独实施，现有上传、列表、详情和下载保持兼容。
