# ADR 0001：后端基础与部署边界

状态：已采纳

## 决策

- 使用 Python 3.12、FastAPI、SQLAlchemy 2、PostgreSQL 与 Alembic；uv 锁定 Python 依赖。
- 生产形态由 FastAPI 同时承载构建后的 React 静态文件和 `/api/v1`，简化单机部署；开发时由 Vite 代理 API。
- 当前是单一主人账号，但表结构以 UUID 用户主键和独立会话表保留未来多人能力。以后每个业务表都必须有明确的用户归属，不能把“当前只有一个人”编码成全局数据。
- 不提供公开注册。主人账号通过后端命令初始化，数据库约束保证最多一个主人账号。
- 使用 Argon2id 密码哈希、随机不透明会话令牌、数据库中只保存令牌摘要、HttpOnly 会话 Cookie、双提交 CSRF 和 Origin 校验。登录按“请求来源 + 规范化账号”组合在单进程内节流，失败响应保持一致，避免仅凭用户名锁死唯一主人；公网及多进程部署前仍需把同一策略放到反向代理或共享限流层。生产 Cookie 必须启用 Secure，HTTPS 由未来反向代理终止。
- 当前不引入 Redis、任务队列、微服务或数据库行级安全。真实佳明、上传、AI 和运动业务接口属于后续独立里程碑。

## 原因

该组合与佳明生态常用 Python 库兼容，同时保持单进程部署简单。用户与会话分离让当前单用户体验不会阻断后续多人协作。把业务能力留在范围外，避免在数据契约、权限和安全边界尚未确认时制造不可逆实现。

## 后果

- 登录已成为真实跨端能力，受保护路由不再只依赖浏览器本地状态。
- 单机 Compose 是当前开发和预览基线；正式部署仍需域名、TLS、密钥管理、备份和监控配置。
- 任何新增业务模型都必须显式设计 `user_id`、授权查询和迁移测试。
