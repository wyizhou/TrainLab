## 0. 作用与权威顺序

本文件用于控制后续各层开发会话的顺序、边界和验收，解决重复开发、跨层代写、
测试反复全跑和“单元完成却又被当成未开始”等问题。

权威顺序如下：

1. 五份已冻结大契约决定业务语义、表所有权、公共接口和安全边界。
2. 各层详细开发清单决定该层单元的完整需求和完成证据。
3. 本文件决定跨层依赖、执行顺序、共享文件所有权、验证层级和最终集成归属。
4. 若本文件与冻结大契约存在语义冲突，以冻结大契约为准并停止相关开发；不得由任一
   层会话自行“兼容”。

本轮只更新规划文档和状态索引。本文中的所有未来单元均为 `[ ]`，不表示已经执行。

## 3. 五层合理性复核结论

### 3.1 已确认合理且保持不变

1. 第一层是一次性、幂等的数据基础初始化；ready 后严格 no-op，不成为常驻服务。
2. 第二、三、四层都是调用一次、完成后退出的 tools；只有第五层可以常驻和调度。
3. 第二层持久化有效 FIT，不长期保存下载 ZIP；ZIP 只在安全校验和提取期间临时存在。
4. FIT 是活动传感器、开发者字段和专项结构的首选来源；Connect JSON 保留远端 ID、
   用户修改和 Garmin 后处理结果。
5. 第三层拥有分析、训练计划和主动分析邮件；第四层拥有入站邮件、用户事实、AI 回复
   和回复投递；第五层只发送独立运维告警。
6. 第四层不能代发第三层产物，第五层不能直接写第二至第四层业务状态。
7. 同一个 SQLite 是结构化权威来源；UTC 保存时间，以 `Asia/Singapore` 推导日期。
8. 当前生产旧入口继续存在，只有影子对账、受控验收、明确批准和回滚演练完成后才切换。

### 3.2 已发现并在总控顺序中修正的问题

1. 各 README 和详细清单头部状态滞后，错误显示“未开始”。状态索引应反映已有完成项，
   但不得改动冻结大契约哈希。
2. 第五层依赖图重复定义 `S5-18`，且视觉上可能让人误以为工作流先于统一 receipt
   分流。正确顺序是 `S5-11 → S5-08/09/10/12/13`。
3. L2-17、A3-23、M4-14 和 S5-10 都包含跨层验收，若各层分别写端到端测试，会重复
   定义协议甚至互相修复。后续由总控 `X-*` 单元唯一拥有跨层端到端验收；各层只提供
   自己的公共 contract fixture。
4. M4-14 与 S5-10 存在完整联调上的循环等待。M4-14 分为：
   - `M4-14A`：第四层基于冻结 DTO 和 fake orchestrator 的提供方合约；
   - `M4-14B`：S5-10 完成后的真实合成闭环验收。
   M4-14 只有 A/B 都通过后才可整体勾选。
5. 第一层的 `raw_objects/source_revisions` 是共享物理表，但不是“谁都能写”的共享领域。
   第二层只能写 Garmin namespace，第四层只能写 Gmail namespace；DDL/迁移仍只归第一层。
6. `src/trainlab/cli.py`、`src/trainlab/mcp.py`、依赖锁、共享 Harness 和共享 Schema
   manifest 是集成热点，不能交给多个层会话同时修改。
7. 过去每个小修复都重复跑大范围测试，容易形成循环。后续采用分级验证和明确的重开条件。

### 3.3 没有发现的冲突

- “第三层主动发送分析邮件”与“第四层处理收件和回复”目前边界一致。
- “第五层总调度”与“第二至第四层无定时能力”一致。
- 第一层的健康、活动、邮件、分析/计划和运维表能承载当前四个运行层的权威数据。
- 当前公共 mode/status 集合可覆盖计划中的同步、分析、邮件处理、恢复和编排流程。

| Garmin raw/revision namespace | 第二层 | 其他层只读有界状态 | 第四层写 Garmin 对象 |
| Gmail raw/revision namespace | 第四层 | 第三层只读已门禁事实 | 第二层写 Gmail 对象 |

不能把共享文件加入原业务单元的默认写入集合。

- 前置为 A3-19、M4-14A、S5-10。
- 本单元同时构成 M4-14B、A3-23 和 S5-10 的跨层证据，但每份证据只存一份并以 ID 引用。
- 禁止第四层声称未成功的计划已修改，禁止第五层传递自由邮件正文，禁止重复计划邮件。

### [ ] X-05｜全离线合成端到端门

- 覆盖 weekday morning、Sunday、普通邮件、计划修改邮件、deferred、auth_required、
  lock_busy、delivery unknown、Supervisor restart 和 incident。
- 所有 Garmin/Gmail/Codex 均为 fake；禁止真实网络和生产数据库。
- 每种业务对象必须证明唯一 workflow/run/artifact/plan/response/delivery 身份。

### [ ] X-06｜Shadow、真实验收与生产切换门

分成三个不可合并的阶段：

1. `X-06A shadow`：无真实副作用，对账新旧日期、对象和调度结果。
2. `X-06B controlled live`：取得逐项授权后才运行最小真实矩阵。
3. `X-06C cutover`：备份、唯一调度验证、go/no-go 批准和回滚演练后才切换。

任一阶段失败都停止后续阶段；不能用“真实调用成功一次”替代 shadow、幂等和回滚证据。

## 7. 允许的并行与默认串行规则

默认只允许一个活动开发单元。采用“先完成一层，再进入下一层”的主线：

```text
BASE-00 → W2 → W3 → W4 → W5 → X-01..05 → X-06
```

仅在满足下列全部条件时允许并行：

1. 两个单元都从同一个不可变 `BASELINE_ID` 建立独立 branch/worktree。
2. 写入文件集合、数据库表所有权和公共 Schema 完全不重叠。
3. 两个单元之间没有未完成的接口依赖。
4. 已指定合并顺序、集成负责人和失败回退点。

可并行示例：

- 已冻结 provider fixture 后，第三层 runner 单元与第四层 reply publisher 单元可在不同
  工作树开发，但默认主线仍按层串行。
- 只读审计、静态安全扫描和文档复核可以并行。

禁止并行示例：

- 任意同时修改 `src/trainlab/cli.py`、`src/trainlab/mcp.py`、依赖锁或共享 Harness。
- A3-19、M4-14B、S5-10 同时各自实现完整计划修订闭环。
- 多个单元同时迁移 Foundation schema 或写同一张运行表。
- 在共享未提交工作树上启动多个写入型开发会话。

## 8. 分级验证和停止反复规则

### 8.1 验证层级

| 层级 | 何时执行 | 内容 | 执行频率 |
|---|---|---|---|
| V0 静态 | 每个单元 | 格式/编译、Schema/hash、禁止 import/路径、diff 检查 | 每次候选交付 |
| V1 聚焦 | 每个单元 | 该单元新增/受影响测试和故障注入 | 每次候选交付 |
| V2 单层回归 | 一个层内波次结束 | 该层全部已完成单元测试 | 每个集成门一次 |
| V3 跨层合约 | X-01～04 | DTO、ID、日期、所有权和恢复链 | 每个跨层门一次 |
| V4 全离线 E2E | X-05 | 五层 fake 端到端 | 进入 shadow 前一次 |
| V5 受控真实 | X-06B | 最小 Garmin/Gmail/Codex/systemd 矩阵 | 明确授权后一次 |

### 8.2 失败后的重跑规则

1. 首次失败只修复失败单元，并把复现加入永久聚焦测试。
2. 修复后先重跑失败用例和 V1；通过后再在集成门执行一次 V2。
3. 不因为一个下游失败重做所有已完成上游单元。
4. V4/V5 失败时记录精确对象 ID、阶段和回退状态；不能反复发送或重建业务对象试错。

### 8.3 已验收单元的重开条件

已完成单元只有满足以下至少一项才允许重开：

- 对应冻结契约或公共 Schema 哈希发生经批准的变化；
- 新增永久回归测试能稳定复现该单元缺陷；
- 下游公开接口合约测试证明该单元输出不兼容；
- 安全、隐私、数据完整性问题要求立即修复。

普通状态复核、文档措辞变化、其他层尚未完成或“想再保险检查一次”都不构成重开理由。

## 9. 每个开发会话的交付回执

后续会话完成一个单元时必须返回以下有界信息：

```text
unit_id:
baseline_id:
contract_hashes:
changed_files:
owned_tables_or_namespaces:
forbidden_scope_check:
focused_validation:
layer_gate_validation:
new_regression_tests:
known_failures:
external_side_effects: none | exact authorized actions
rollback_point:
next_unblocked_units:
```

缺少 `baseline_id`、修改了未授权共享文件、没有聚焦验证或无法说明回退点的交付，不得
合并，也不得把清单改为 `[x]`。

## 10. 总体完成定义

TrainLab 目标五层架构只有同时满足以下条件才可称为完成：

1. 五份冻结契约仍匹配，或已有显式版本升级和影响重评审。
2. 各层全部开发单元与正式门有可复现证据，不以文档勾选代替测试。
3. X-01～X-05 全离线通过，且没有跨层写入、重复投递或双重调度。
4. X-06A shadow 对账完成，所有差异可解释。
5. X-06B 获明确授权并完成最小真实验收，敏感信息未进入日志/报告。
6. X-06C 有备份、go/no-go 批准、唯一调度验证和可执行回滚。
7. 旧生产入口只有在切换成功后才淘汰；切换失败时能够恢复且不丢失运行审计历史。
