# 同步日历与分页账本

当前模块提供内部 Python 接口，已由 FIT 同步编排复用同一分页生成器并连接下载；
验收使用合成 Provider，尚未发送邮件或启用真实在线任务。
`inventory_complete` 是“活动成员查完了”，不等于“FIT 已全部下载”。非空成员列表的
`collection_complete` 始终为 false，后续下载器才能形成完整同步回执。

## 日期和状态

| 内容 | 当前规则 |
| --- | --- |
| 每日槽位 | 香港时间 22:00；22点前最近到期槽位仍是昨日 |
| 每晚目标 | 当日、昨日，以及启动时登记且尚未完成查询的缺口日 |
| complete | 该日已经结束，且查询的全部分页成功，允许明确“无活动” |
| provisional | 当日仍未结束，分页虽已走完也不代表当天最终无活动 |
| gap / unqueried | 已登记待补查 / 没有查询证据；均不得伪装成无活动 |
| 周统计 | 最近两个周日15:00之间的半开窗口，按活动结束时间归属，不拆活动 |
| 下周计划 | 统计截止后的周一至周日；错过多周只选择最近一期，发布器不得排过去课程 |

`record_gaps` 只登记状态，不调用网络；`pending_days` 给出晚间待查日期，不自行启动任务。
有过完整查询的日期不因保存了旧 gap 行而继续算缺口；当天和昨日仍始终复查。
日历函数尚不是已经启用的守护进程、补发邮件或 Garmin 排期器。

## 可恢复查询

- 一个内部请求冻结逻辑键、日期范围、观察时间、页大小和调用上限。
- 每次领取调用先持久化参数和预算，再调用注入的只读 Provider；页内容只接受活动引用和
  活动日期，不保存名称、GPS、凭据或未声明字段。
- 页号、范围、has_more、重复活动及跨页重复必须验证；空页不能声称还有下一页。
- 完整合法页面立即保存。连接或格式错误结束本次执行，不在同一执行内自动重试；下一次
  显式恢复仍使用剩余预算，从尚未保存的页继续。成功请求重放不调用 Provider、不新增账本。
- `provider_calls` 记录已持久化领取的尝试预算，是崩溃情况下实际调用数的保守上界；
  `unresolved_calls` 单列尚无本地结果的领取。不能把这种不确定性描述成精确远端调用证明。
- 已保存最后一页但回执未完成时，恢复直接从保存的页生成回执，不重查。部分页不能写入
  complete/provisional 日状态。查询完成也不是远端历史数据永不再变化的保证。

## 新库升级

新实例 Schema v2 增加 sync_jobs、sync_calls、sync_results、sync_days、sync_gaps，均保留
不可变历史。旧 M12 v1 实例必须显式调用 `storage.upgrade(instance_root)`；普通打开不会自动
迁移。升级使用新库自己的单写者锁和 SQLite 事务，有限失败回滚全部新增表及版本号。
原正式旧库 `trainlab.db` 不在升级路径中，之前真实复制的 v1 私有实例也没有在本模块中改动。

本接口接受的页大小和预算仍要由后续真实任务授权绑定；内部函数不是任意在线调用的授权。
整次同步的耐久总墙钟与调用/下载/会话上限由[同步编排](fit-sync.md)统一管理，
不在日历函数中复制第二套时间状态机。
