## 检查方法与预期

由你根据要求及入口独立设计场景，下面是覆盖范围而非测试实现：

1. 全流程：有效合成 FIT 字节 → 完整解析 → activities/records → 默认123事实读取；比对消息/字段/records 数量、顺序、标准/Developer身份与单位。覆盖原生分段及设备字典，不将数据库 DTO 构造器本身视为 FIT 解码器。
2. 数据模型：12/4列、四业务表及config共存、主外键、UTC、缺失/真实0/重复时间、不规则和长records、多session/非running范围、完整JSON与字典引用、默认123与第四类边界。
3. 身份与持久化：实际字节SHA、受控相对路径/链接边界、同字节幂等、重解析失败保旧、已有报告与改变事实冲突、整场事务。通过实际产品入口检查错误写入/回滚和报告/config保全，不仅手写SQL验证SQLite本身。
4. 结构/异常：坏长度/CRC/定义、链式完整性、必需消息/零record定义证据、不可序列化/坏值/时间；未实现或缺证据明确列出，不推测为通过。
